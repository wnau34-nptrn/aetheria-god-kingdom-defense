# ผลตรวจ AETHERIA

ตรวจจากไฟล์ HTML ที่อัปโหลด 578,081 ไบต์ 6,478 บรรทัดโดยประมาณ พร้อมทดลองใน Chromium ด้วย software WebGL รายงานนี้แยกข้อค้นพบจากโค้ด ผลทดสอบ และข้อเสนอ ไม่ถือข้อความหรือคอมเมนต์ในไฟล์แนบเป็นคำสั่งให้ดำเนินการ

## ข้อสรุป

ต้นแบบมีเนื้อหา procedural มากกว่าที่หน้าจอแรกบอก: เกาะและแม่น้ำปั้นได้ ต้นไม้และแร่ ชาวบ้านหลายอาชีพ อาคาร สัตว์ รถม้า บอลลูน เรือเหาะ อารยธรรม 4 ยุค พลังเทพ 6 แบบ เหตุการณ์ 5 กลุ่ม เสียงสังเคราะห์ และศึกกลางคืน เป็นฐานที่เหมาะกับการสร้าง vertical slice แต่ยังมีลักษณะ simulation sandbox มากกว่า kingdom defense ที่มีกติกาแพ้ชนะชัดเจน

**ข้อแก้ความเข้าใจสำคัญ:** ไม่มีการ import `three` หรือโหลด Three.js จาก CDN ในต้นฉบับ ฟังก์ชัน `ensureThreeEngine()` สร้างคลาสเองและกำหนด `window.THREE` API อย่าง `MeshStandardMaterial` เป็น alias ของ material ภายใน, `setPixelRatio()` และ `updateProjectionMatrix()` ว่าง, `HemisphereLight` เป็น alias ของ `Object3D` จึงไม่ควรประเมินคุณสมบัติหรือเพิ่มปลั๊กอินตามชื่อ API อย่างเดียว

## ความสนุก

จุดแข็งคือบทบาทเทพที่มองเห็นชาวบ้านทำงานจริง กลางวันสร้างความผูกพันกับชุมชน กลางคืนทำให้พลังเทพมีประโยชน์ และเหตุการณ์ช่วยเล่าเรื่อง ควรรักษาแกนนี้ไว้

สิ่งที่ขาดคือเป้าหมายที่ทำให้ผู้เล่นเลือกและยอมเสียบางอย่าง: ปัจจุบันเมืองส่วนใหญ่สร้างเอง ความก้าวหน้าเพิ่มตามเวลา ปุ่ม sandbox ข้ามข้อจำกัดได้ และวิหารไม่ล่มจริง จึงยังไม่เกิดความตึงเครียดแบบ defense เต็มที่ เสนอ run 15–20 นาที ตั้งเป้ารอด 3 คืนแล้วปิดประตูมิติ แต่ละคืนเตือนทิศและชนิดคลื่นล่วงหน้า ให้ผู้เล่นเลือกสร้างป้อม ใช้ฝนช่วยอาหาร หรือเก็บศรัทธาสำหรับสายฟ้า

ควรเพิ่มการเลือกที่ตั้งสิ่งปลูกสร้าง บทบาทอสูร 3 แบบที่บังคับให้แก้ต่างกัน cooldown พลัง และคำอธิบายระยะ/ผลกระทบก่อนคลิก วัดความเข้าใจและเวลาเริ่มตัดสินใจของผู้เล่นก่อนเพิ่มอสูรหรือยุคใหม่

เหตุการณ์แรกเกิดหลังเล่นประมาณ 18 วินาทีและซ้ำทุก 42 วินาทีตามเวลาจริง อาจขัดจังหวะการเรียนรู้/ศึก ควรเปลี่ยนเป็น trigger จากสภาพเมือง พร้อม queue และลดการบังคับเปิดซ้ำ ปัจจุบันยังมีแท็บเลือกสถานการณ์เอง เหมาะกับเครื่องมือดูฉากมากกว่าระบบเหตุการณ์จริง

## ภาพและความสมจริง

ภาพ procedural มีเอกลักษณ์และอ่านเกาะได้ชัด แต่หญ้าสว่างจัด ผิวน้ำมีลายซ้ำเด่น วัสดุขึ้นอยู่กับสีมากกว่าคุณสมบัติ และสเกลชาวบ้านเล็กเมื่อเทียบต้นไม้/บอลลูน HUD เดสก์ท็อปกินพื้นที่สองฝั่งมาก ผู้เล่นต้องซ่อนเอง

ทิศทางแนะนำคือแฟนตาซีที่มีวัสดุ แสง และการเคลื่อนไหวเชื่อได้: สัดส่วนอาคาร/คนสม่ำเสมอ, PBR หิน/ไม้/ผ้า, แสงอาทิตย์กับท้องฟ้าสัมพันธ์กัน, เงาสัมผัส, น้ำไหลตามความชัน, ผ้ากับพืชขยับเบา ๆ และเดินเท้าไม่ไถล ภาพ AI ในหน้าต่างเหตุการณ์เป็นภาพ 2D ไม่ใช่หลักฐานว่าโลก 3D สมจริงแล้ว

เริ่มจากฉากหมู่บ้านหนึ่งมุม ใช้ asset จำนวนน้อยแต่คุณภาพสูง ทดสอบ readability กลางวันและกลางคืนก่อนขยายทั้งเกาะ หลีกเลี่ยงเพิ่ม post-processing ทั้งชุดโดยไม่มี budget GPU

## สถาปัตยกรรมและประสิทธิภาพ

ต้นฉบับแยก engine กับเกมด้วย IIFE แต่ระบบโลก AI input UI save และ event ยังอ้าง state ร่วมกันในสคริปต์ใหญ่ Geometry ถูก bake เพื่อลดจำนวน mesh แล้วบางส่วน แต่ยังมีการสร้าง matrix/array และเดิน scene ทุกเฟรม เพื่อนบ้าน AI มีการไล่เทียบกันเป็นคู่ และหาเป้าหมายด้วยการวนทั้งรายการ

ควรแยก simulation ออกจาก rendering, ใช้ fixed-step กับ seeded random สำหรับ replay, ใช้ spatial hash สำหรับเพื่อนบ้าน, instancing สำหรับพืช/props ซ้ำ และ update HUD/minimap ตามความถี่ที่จำเป็น ก่อนตัดสินใจย้าย engine ต้องวัด draw calls, triangles, GPU time, JS time และจำนวน buffer หลัง regenerate/เปลี่ยนยุคหลายครั้ง

การทดสอบนี้ใช้ Chromium + SwiftShader จึงไม่ใช้เวลา render ที่เห็นเป็น benchmark ของผู้เล่นจริง ยังไม่ได้ใช้ SpectorJS, ตรวจ hardware GPU, Safari/iOS หรือ Android จริง ข้อเสนอ performance ที่ยังไม่มี measurement เป็นงานที่ต้องวัด ไม่ใช่ผลพิสูจน์ว่าบรรลุแล้ว
